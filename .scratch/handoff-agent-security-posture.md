### Findings (drive the tighten phase)

1. **`IamScopedVerification` resource ARNs are broken for SSO roles.** Actual role ARNs include the SSO path: `arn:aws:iam::741297776185:role/aws-reserved/sso.amazonaws.com/us-west-2/AWSReservedSSO_agent-ai_d3ae8eca9c6db8bc` (admin set: `.../AWSReservedSSO_AWSAdministratorAccess_3780b855f22f7e4e`). The patterns `role/agent-ai-*` and `role/AWSAdministratorAccess-*` match nothing — IAM role ARNs include the path. Masked by `ReadOnlyAccess` today; **once the fallback is removed, `GetRole`/`GetRolePolicy`/`ListAttachedRolePolicies` on these roles will be denied.** Fix: `role/aws-reserved/sso.amazonaws.com/us-west-2/AWSReservedSSO_agent-ai_*` (plus the admin-set twin), or `role/aws-reserved/sso.amazonaws.com/*` for all SSO roles. **RESOLVED in v2 (2026-11-28):** ARN fixed to `role/aws-reserved/sso.amazonaws.com/us-west-2/AWSReservedSSO_agent-ai_*`; the admin-set twin was **dropped** (the agent has no business introspecting the admin role).
1. **CloudTrail role-name assumption wrong:** roles are `AWSReservedSSO_<set>_<hash>`, not `agent-ai-<id>`. Any CloudTrail audit filter for "the agent" must match the `AWSReservedSSO_agent-ai_` prefix.
1. **Quotas/budgets absent from final policy** (dropped at provisioning). Action names re-verified against the local CLI service models 2026-11-27 — use these, not the earlier draft list: reads = `service-quotas:ListServices` / `ListServiceQuotas` / `GetServiceQuota` / `ListRequestedServiceQuotaChangeHistory` / `ListRequestedServiceQuotaChangeHistoryByQuota` / `GetRequestedServiceQuotaChange`; `budgets:DescribeBudgets` / `DescribeBudget` / `DescribeBudgetPerformanceHistory`; `ce:GetCostAndUsage` / `GetCostForecast` / `GetUsageForecast` / `GetDimensionValues`. **Retracted (did not exist):** `service-quotas:RequestServiceQuotaChange` (real: `RequestServiceQuotaIncrease` / `CreateSupportCase`) and `service-quotas:GetServiceQuotas` (real: `GetServiceQuota` + `ListServiceQuotas`). Re-add only if the model-gate (spend guard) or invoke-path tracks need them — via the proposal/approval loop (see Process note), not by assertion. **Live-verified 2026-11-27 via `ai-admin` (admin set, same account):** `service-quotas list-services` ✅ (services list returned); `budgets describe-budgets --account-id 741297776185` ✅ exit 0, **empty body = no budgets configured** — if the spend guard uses Budgets as the mechanism, a budget must be created first; `ce get-cost-and-usage` ✅ (Nov 2026: $0.008 unblended — data flowing, account near-dormant). Note: first attempt at all three failed on **my** missing params (region / `--account-id` / `--metrics`) — clean local-validation errors under `ai-admin` vs. the AccessDenied false-signal `ai-agent` would have produced. **RESOLVED in v2 (2026-11-28):** all three spend-guard read statements added (reads only, `Resource: *`). Budgets still empty in-account — the guard needs a budget created before it has data to describe.
1. **MCP sandbox gap:** `access-analyzer` is unsupported in `mcp-proxy-for-aws-cli` (the CLI command is `aws accessanalyzer`); works fine via CLI. Tooling gap, not a permission gap.
1. **`iam:ListRoles` cannot be resource-scoped.** Account-level action — the statement's `Resource` must be `"*"`; the role-ARN list in `IamScopedVerification` can never match it (same class of bug as Finding 1). Masked by `ReadOnlyAccess` today; after the fallback is removed, `ListRoles` would be denied under the current statement. Split into its own statement, or drop if unneeded. **RESOLVED in v2 (2026-11-28):** split into the `IamAccountLevel` statement.
1. **Process (user-directed 2026-11-27):** never assert "action X exists" — verify against the local CLI service model (`aws <svc> help`) before proposing it in a policy. Live checks against the account: agent proposes the exact call(s), user reviews/approves (and may run) under the privileged `ai-admin` profile. This shortens the feedback loop and removes guesswork about how work is carried out. **Safety step (2026-11-28): the user's approval prompt on every `aws` CLI call IS the review gate** — do not self-impose one. And pick the profile for the signal you want: surface-validation under `ai-admin` (privileged ⇒ a failure is a clean signal — bad name / not enabled / wrong region); effective-grant checks under `ai-agent` **after** the statement is in policy (under `ai-agent` today, AccessDenied would be a false "action doesn't exist" — the exact mode retracted twice).
1. **SSO-role policy attach/detach = Identity Center / mgmt account, not the local CLI.** `detach-role-policy --role-name aws-reserved/sso.amazonaws.com/...` fails — the CLI's `--role-name` validator rejects the dots in `sso.amazonaws.com`. The user detached `ReadOnlyAccess` via Identity Center (mgmt account) instead. Rule: change *what's attached to an SSO role* ⇒ Identity Center / mgmt account; change the *policy document* (`create-policy-version`) ⇒ fine via CLI (how v2 landed).
